# 角色扮演技能（多 Agent 跨角色评审）

用多 Agent 扮演不同利益相关者角色（产品 / 架构 / 安全 / 运维 / QA / 法务…），
**针对同一个方案或需求**，从各自立场输出该角色独有的风险、约束与诉求，
最后综合为多角色风险矩阵。评审是单一对象的，视角是多元的。

与头脑风暴（多方案竞争）和辩论（对抗挑错）的本质区别：
**这里的价值是「角色立场互补」，而不是「方案数量」或「对抗强度」。**

## 编排流程

### 第 1 步：选定角色阵容

按评审对象选 3-4 个互补角色（不要贪多，每个角色必须立场具体、可区分），
在 task 中写明每个角色的身份、关注维度与输出格式。

常用角色库（按需组合）：

| 角色 | 关注维度 | 典型质疑点 |
| --- | --- | --- |
| 产品/业务 | 用户价值、范围蔓延、需求理解 | 这个方案解决的是不是真问题？范围是否在膨胀？ |
| 架构/技术 | 扩展性、可维护性、技术债 | 演进路径是什么？会不会把自己锁死在某个技术选型？ |
| 安全/合规 | 攻击面、数据隐私、合规要求 | 敏感数据怎么保护？哪些环节不可审计？ |
| 运维/可靠性 | 可部署性、可观测性、失败模式、回滚 | 出问题怎么发现？怎么回滚？有没有单点？ |
| QA/质量 | 可测性、边界条件、回归风险 | 怎么验证它有效？边界和异常路径覆盖了吗？ |
| 法务/成本 | 许可合规、成本、资源占用 | 许可证兼容吗？隐性成本（人力/资源）是多少？ |

### 第 2 步：并行派发角色评审

对每个角色 spawn 一个 agent（一次 spawn 完，并行执行，不要逐个等待）：

- task 写明：「评审对象【完整方案/需求】+ 你的角色是【X】，立场是【…】，
  请只从该角色视角审查，输出：风险清单（风险/影响/严重度/建议）」
- **角色间禁止交流**——各自独立评审，保证视角不互相污染（这是与会议模式的关键区别）
- 高风险场景可 spawn 一个 role=critic 作为「总批判者」兜底（可选）

### 第 3 步：交叉质疑（可选，高风险场景加一轮）

把各角色意见汇总后，followup_task 唤醒各 agent（或 spawn 质疑者）：
「这是其他角色的意见摘要：{各角色意见}。从你的角色立场出发，
哪些冲突点你坚持、哪些你可以让步？给出理由。」

这一步暴露**角色间真正的冲突**（如：产品要快上线 vs 安全要全量合规），
为最终决策提供依据。注意：交叉质疑只保留分歧，不求共识。

### 第 4 步：综合评审报告（主 Agent 职责）

你（主 Agent）做最终综合，输出：

1. **多角色风险矩阵**：角色 × 风险 × 严重度（表格，可溯源到具体角色）
2. **冲突点与裁决**：哪些角色诉求矛盾，你的取舍与理由
3. **修订建议清单**：按严重度排序，可交付的改进项

不要只转发各角色的报告——**综合与裁决是你的职责**。

## 与其他模式的区别

- 想要**多个方案**（互不污染地提案）→ 用 brainstorm
- 想要**对抗收敛**（迭代修订一个方案）→ 用 agent-debate
- 想要**群聊共识**（互相影响、达成一致）→ 用 meeting
- 想要**角色化视角审视单一方案**、暴露跨角色盲区 → 用本模式

## 纪律

- 角色 3-4 个为宜；每个角色立场必须具体（避免「万金油」角色重复发言）
- 角色间独立评审（并行 spawn，禁止提前看到彼此意见）；只有交叉质疑轮才汇总
- 输出必须标注每个风险来自哪个角色（可溯源）
- 综合评审报告由主 Agent 产出，不得只转发各角色清单
- close_agent 释放已完成的 agent
